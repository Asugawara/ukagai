# public/

The GUI served by `ukagai serve`. Static files, no build step. `GET /` returns `index.html` (and issues the cookie); everything else is under `/public/*`.

- `index.html` — the skeleton (banner, the header `#head`, then the left "background" and right "decision" columns, empty state, drawer for the pending list; toasts are created by `app.js`). Static text carries `data-i18n="<key>"` / `data-i18n-aria-label="<key>"` and is replaced at startup.
- `settings.html` / `settings.js` / `api.js` — the settings page at `/settings` (see "Settings page" below). `api.js` is the tiny `api()` fetch wrapper it shares (cookie renewal on a 401).
- `i18n.js` — ES module with `MESSAGES = { en, ja }`, `t(key, vars?)` and `applyStatic()`. Both languages must have the same key set (tested). Keys are English snake_case; `{name}` marks a variable.
- `app.js` — ES module. API calls, SSE, rendering. Text from outside is inserted with `textContent`. Every display string goes through `t()`.
- `app.css` — system fonts. The body grid is banner / header / main. Below the header, two columns (background 3fr / decision 340–520px), one column below 900px (decision first). Dark mode follows `prefers-color-scheme`.
- `vendor/` — `mermaid.min.js` and `marked.umd.js` (committed; no CDN). The only CDN use is optional syntax highlighting: highlight.js from cdnjs (`github` / `github-dark` by `prefers-color-scheme`); without network code blocks stay plain.

Update vendor with `npm ci`, then `npm run vendor` (copies from `node_modules` to `public/vendor/`).

## Tabs

- A tab the server opened (`/?autostart=1`, see `POST /api/gui/open`) strips the query at startup (`history.replaceState`) so a tab pinned later is clean. Every tab talks on `BroadcastChannel("ukagai-tabs")`: it posts `hello` on load and answers `anyone` with `here`. The auto tab posts `anyone` and calls `window.close()` on the first `here` / `hello` from another tab within `AUTO_CLOSE_WINDOW_MS` (5 s) of its load; after that, and in a tab without the flag, nothing closes. Without `BroadcastChannel` nothing changes. `/settings` is untouched.

## Tab icon

`favicon.svg` (and a 32×32 `favicon.png` fallback, rendered from it with `rsvg-convert`) is the static icon: a white "u" on the accent-blue rounded square; `GET /favicon.ico` answers 204. `app.js` `updateFavicon(n, blocked)` is called from `renderHeader()` with the same pending count as the title: at 0 the static icon stays, from 1 it draws the square on a 64×64 canvas (canvas primitives, no SVG load) with the count in white bold sans, `5+` from 6 on, red instead of the accent while a blocker waits, and swaps the `link[rel=icon]` to the PNG data URL (the PNG fallback link is taken out meanwhile). It is always on (not tied to `notify.title_badge`) and redraws only when the count or blocker state changes. Without canvas support the static icon stays.

## Settings page (`/settings`)

`GET /settings` serves `settings.html`; `settings.js` builds one column of fieldsets (Display / Progress checkpoints / Plans / Notifications) from `GET /api/settings` and saves each control on change with `PUT /api/settings` (the whole object; a small "Saved" status, an inline message for an invalid value, the controls re-render from the saved state). The theme applies at once (`<html data-theme>`), a language change re-renders the page in the new language, `Esc` goes back to `/`. Turning on the browser notification asks the browser for permission and stays off unless it is granted; the permission state is shown. The strings are the `set_*` keys of `i18n.js`.

`app.js` loads `/api/settings` before the first render and on SSE `settings.updated` (`applySettings`): `theme` (`data-theme`, and the highlight.js / mermaid theme), `hints` (`body.no-hints` hides the footer), `plans.auto_show` (`queuedPlans()` keeps new plans out of the queue and the Pending count, and with it on still only the plans that carry a `session_id`: a plan file whose session is unknown is never shown by itself and is only in the drawer until `plan.updated` brings the session; `drawerIds()` still lists them, and the Pending button stays visible while a plan waits so the drawer is reachable), `notify.*` (a WebAudio beep through one shared `AudioContext` that is created / resumed on the first key or click (a context made without a gesture starts suspended) when the tab is not focused, a `Notification` when it is hidden, the `(N)` title badge: `title_badge=false` drops only the count, the "waiting" cue of a blocker stays). Typed drafts are stashed (`stashDrafts()`) before the page changes. The `,` key and the `Settings` link in the header's meta area (`#settings-link`, floating at the top right while there is no header) open `/settings`; the hint line lists `, Settings`.

Dark mode: `app.css` defines the dark variables for `prefers-color-scheme: dark` (unless `data-theme="light"`) and for `data-theme="dark"`; the server injects `data-theme` into the page when it is pinned.

## Display language (`data-lang`)

The display language is `en` (default) or `ja`. The server keeps the live settings (loaded from `<data-dir>/config.json` at startup, replaced by `PUT /api/settings`) and injects `<html lang="…" data-lang="…">` into `index.html`; `GET /api/config` returns `{ "lang": "ja" }`. `app.js` reads `document.documentElement.dataset.lang` (anything but `ja` means `en`), applies it to the static text, and renders with `t()`.

- Changing `dataset.lang` at runtime re-renders in place (a `MutationObserver` on `data-lang`). The tests use this instead of reloading.
- UI strings are translated, and so are the headings of the **known sections** (Recommendation / Options / What I checked / What you need to do / Scope and reversibility / Terms / Assumptions / Counterargument / Affected / What only you know): whichever language the file's heading is in, the right column and the left column show the display language's wording (`sec_*` keys). Headings the GUI does not know (and "Why this decision is needed now", "Diagram", "Related diff") stay as written.
- Explanation files are accepted with English headings (canonical) or Japanese headings (alias). `app.js` keeps constants with the same content as `SECTION`, `BLOCKER_LABELS`, `COLUMN_HAPPENS`, `COLUMN_RISK` and the risk-word lists (`UNDO_BAD_WORDS` / `UNDO_WORDS`, the `undo` check; N0 vocabulary, same text as `src/hook/explain.ts`) in `src/hook/explain.ts`: sections are matched by exact name over all names, then by partial name; table columns by `happens|outcome|起きること` and `risk|リスク`. Keep them in sync.

## Behavior

- One screen: the page does not scroll, only the columns do when content does not fit. The layers are **header = 1 second, right column = choose, left column = doubt and verify**.
  - **Header (`#head`, full width, above both columns)** is exactly two rows for every card kind (the title is the only large text; GOV.UK question pages / Material 3: one title, the rest smaller). **Row 1 (`.hd-title`)** is the **title** (`.v2-title`, 20 px / 600, one or two lines ending in `…`; a click on it or `.` shows all), then the reversibility mark only when it is not reversible (`◐ Costly to undo` / `■ Irreversible` are the only boxed things in the header; a reversible card says nothing). **Row 2 (`.hd-ctx`, 12 px, `--fg`)** is the chips `● repo` `⎇ branch` `⧉ worktree` `scope` `age` (`.chips.hd-where`; the dot is in the repo colour, the working directory is the tooltip on the repo chip; the plan prompt's stats chip `9 sections · 219 lines · 14 files` and file name follow the age on an approval); at its right end sit a small "Show all" text button (only when something on the screen is folded), the pending-count button `☰ N` (with 2 or more pending; the count only, no word; its accessible name is "Pending decisions") and the Settings link (`.hd-meta`). A blocker's / quiz's band is this row's background and its label ("Waiting for you" / "Quiz") opens it; the title row stays on the panel. **The top of the left column** carries what used to sit under the title, in this order: the **Goal row** (see "Session history"; absent without history), a checkpoint's note, the **headline** (`.headline`, 14 px normal weight: the first sentence of the Recommendation; for a plan the prompt "Approve this plan?", for a raw question the question when it differs from the title, for a quiz its last paragraph; two lines, a click or `.` shows all; a checkpoint has none because its recap is the body) and the **condition** (X1: the last sentence of the Recommendation when it holds a condition word (`RECOMMEND_COND`, same regex as `src/hook/explain.ts`) and is not the headline itself, with a 600 `Condition` / `条件` label (the text unchanged) (ja `ただし: …`); absent without one). `context.branch` is the only context field rendered. Drawer rows start with a dot in the repo colour, then the repo in bold. **Repo colour**: the repo name (the working directory's last segment when there is none; `plans/` for the plan screen) is hashed (FNV-1a, 32 bit) to one of 12 slots, hue = (238 + slot × 27) mod 360 (skips 200–235, the UI accent blue; `plans/` is a neutral grey via `--repo-sat: 0%`; `repoSlot` in `app.js`, the same algorithm as `repoSlot` in `src/tui/model.ts`, which gives each slot the nearest of 6 ANSI colours for the TUI; `plans/` is grey there too). `renderHead` sets `--repo-hue` on `#head`; `.hd` turns it into `--repo-accent` (`hsl(hue 70% 28%)` light / `74%` dark) and draws a 3 px left border in it; the dot (`.repo-dot`) takes the colour too. A blocker's orange band keeps its place and the repo colour stays as the left border. Checkpoint cards and approvals use their session's working directory. There are no metrics or session list.
  - **Right column (`#decision`)**: only the choice. The option cards (a number `1`-`4` at the left, recommended badge, the title 600, "what happens" 400 as the body, "risks" in the same size with the red marks), None of these / Can't answer, free text and the one-line hint at the bottom. **There is no Answer button** on a single select (see "Select = send"); multi select and several questions keep one. Bodies fold at 2 lines; the card under the cursor always shows everything. Nothing from the old top panel (recommendation box, You decide, Assumptions, Against, Affected) is here, and there is no row of label chips: an option label appears once, on its card.
  - **Left column (`#background`)**: starts with the **lead** — Why this decision is needed now, the rest of the Recommendation (after the headline; callouts inside the frame), You decide, Against, Assumptions (X1 order: context first, then the pick) — followed by Why / What I checked / Diagram / Related diff / unknown sections as written, and last a folded "Affected (N)" row (closed by default; opened, a vertical list of `code`, every item). The Terms list is the `?` overlay. The column scrolls.
- **The GUI builds the decision screen from the explanation file. A raw AskUserQuestion is shown only without an explanation (`attached_via: none`).** The spec is explanation file v2 (`title`, the Recommendation section, the Options table).
  - Option cards are one per table row; the `(Recommended)` suffix is stripped and the recommended one gets a badge. The original question and `description` are not shown for options matched to the table (an option with no row falls back to its raw label and description; with several questions each question is headed in the right column). The answer is the original `option.label`, not the table's rendering.
  - Without an explanation the left column shows one line saying the agent wrote none, with the reason in plain text when known.
  - Old-format tables (pros/cons/cost) still work: the second and later columns are shown in order as body text.
  - **Auxiliary context (`context`) is not rendered**, except `branch`.
- **Blocker (waiting for human work; `explanation.type === "blocker"` or `type` in the front matter)**: same header; the orange band is the background of the header's context row (row 2), with a "Waiting for you" label. The "what you need to do" section is at the top of the right column (orange frame; code blocks get a Copy button, and key `c` copies the first one via `navigator.clipboard`), then the three fixed cards. No recommendation section means no recommendation box. The left column keeps "why I stopped" and the rest. The drawer row gets an orange "Action" badge. While a blocker is pending, `document.title` is `(N) ukagai · Waiting for you`. The initial cursor is the recommended option (or the fixed "Done. Continue" label), so `Enter` alone resumes.
- **Plan (`approve_plan`)**: same header (row 1 the title, row 2 the context line followed by the plan meta: for a long plan `9 sections · 219 lines · 14 files`, and the basename of `planFilePath` with the full path as its tooltip; the prompt "Approve this plan?" is the headline at the top of the left column). The right column holds the "Scope and reversibility" section of the plan body (folded at 8 lines; `.` or "Show all" expands; omitted when missing; code blocks over 9 lines fold into `<details>`), then the unread line and **one option list like a question** (`.actions > .opt`, keys `1`-`3`): `1` **Approve (continue in auto mode)** / 承認（auto モードで続行） (`.approve-card`, primary, recommended; Enter / `y` / a click send `{approve: true, set_mode_auto: true}`; there is no separate "Approve and auto"), `2` **Instruct** (`.instruct-card`: preset chips, a text box and Send; always shown; the box takes the focus the moment the selection lands on it — `↑` / `↓`, a click anywhere on the card, a chip, `2` or `i` — with the same rules as the free-text card: `↑` / `↓` leave an empty box and stay with text, `Esc` blurs keeping the text; Enter in the box sends `{instruct: true, text}`; an empty box sends nothing) and `3` **Reject** (`.reject-card`: landing on it opens the reason box `#reason`, focused; Enter with a reason sends `{approve: false, reason}`; an empty reason box closes again when the cursor leaves it, `Esc` closes it keeping the text; `n` / `3` / a click select it). There is no contents list. The plan itself is the left column. Backticked file paths in the plan (a token with a `/`, or ending in a short extension such as `.ts`; `:12` suffixes ignored; not inside code fences) are the same click-to-copy `.cbadge` as the evidence lines.
- **Long plan (PL1).** A plan with more than 2 `##` sections **and** more than 40 lines is folded; a shorter one stays one open document with no contents. Each `##` is one `<details class="plan-sec">`, each `###` a `<details class="plan-sub">` inside it. All are folded except the first `##`; the "Scope and reversibility" section stays folded on the left because the right column shows it. A summary row reads `▸ ☐ Heading … 16 lines · 2 files` (lines of the section with its children; distinct backticked file paths in its prose, code fences excluded) and the mark turns `☑` once the section has been opened (the first `##` and the scope section start as `☑`). An open summary sticks to the top of the left column (an open `###` under it). **Two zones** (long plans; a short plan has only the options): the **plan zone** (left column; the initial zone, with the first section selected: `summary.sel`, a subtle accent edge `#background.zone-on`) and the **options zone** (right column, `#decision.zone-on`; its cursor card has `.cursor`, which is absent in the plan zone). `←` / `h` go to the plan zone, `→` / `l` to the options zone (and `←` in an empty Instruct or reason box does too; the cursor card is remembered, so `→` onto Instruct focuses its box). In the plan zone (outside text fields; sent as `KeyboardEvent`, `o` also works with an IME on) `j` `k` / `↑` `↓` move the section selection (and scroll it into view), `Home` / `End` / `gg` / `G` jump to the first / last, `Enter` / `Space` open or fold the selected section (opening marks it read and puts its heading at the top of the left column), `o` opens everything or, when everything is open, folds everything. In the options zone `↑` `↓` `j` `k` move between the three options, `Enter` acts on the cursor option (Approve approves, Instruct focuses the box, Reject sends a typed reason or opens the box). `y` `n` `i` `1`-`3` act from either zone (and put the screen in the options zone). `[` and `]` are no longer section keys: they cycle through the items like `Tab` (`←` `→` `h` `l` cycle only where there are no zones). **One press approves**: `y`, `1`, Enter on Approve or a click on it sends at once for every plan (unread sections and irreversible plans included; `a` does nothing). The hint line shows the keys of the zone (`↑↓ Section · Enter Open · o All · → Options` / `↑↓ Pick · Enter Decide · ← Plan`). **Unread sections** are information only: while an unread `##` remains, one line `Unread sections (3): Changes, …` (ja `未読 3 節: …`, at most 5 names then `+n`; `.plan-unread`) sits directly above the buttons, updates while sections are opened, and disappears at 0; it never blocks. The state (open, read, selected section, zone) is per decision. The same outline rules live in `planOutline` of `src/tui/plan.ts` (`planOutlineOf` in `app.js` is a copy); `test/gui/fixtures/long-plan.md` is the shared synthetic fixture.
- **Plans flow in like questions (PL3b).** The files in `~/.claude/plans` are items next to the pending decisions; there is no `p` browser. The GUI keeps `plans` (`GET /api/plans` on load and on every SSE reconnect, then `plan.updated` / `plan.removed`) and the bodies it needs (`GET /api/plans/:name`). A plan is **new** when it is unread and its `mtime` is under 24 h old; only new plans that are **`ready`** (the server computes it: session known, session not working, its last Stop not an escaped question, no background subagent running or wake-up turn due, no decision pending, plus the Steps / Verification format only for a session that was handed ukagai's plan rules; never a size threshold) are auto-shown and counted; the others stay in the drawer with a `Writing` / `作成中` label (`.mark.writing`) instead of the `●`, and join the queue when `plan.updated` carries `ready: true`. The Instruct card needs a known session that is not working. The "Pending N" count and the drawer are decisions plus new plans (a plan row: title, `plan` / `計画`, age, `N sections · M lines`, a `●` mark; `▸` when shown). Screen choice when nothing is being looked at: pending decisions, then the newest new plan, then idle; a decision that arrives while a plan is shown takes the screen (the plan keeps its state and is next). `shownId` is a decision id or `plan:<file name>`.
- **Plan versions.** After the human instructs on a plan (the approval card's Instruct / Reject with a reason, or Instruct on a plan file card) the agent rewrites and resubmits it. On an approval card, and on a plan file card whose session is known, `app.js` fetches `GET /api/sessions/:id/plan-versions?current=decision:<id>` (`plan:<name>` for a file) when the card is shown and again on `decision.created` / `plan.updated` / after an Instruct (`loadVersions`, one request at a time, redrawn only when the versions changed). With **2 or more versions** the left column starts with a bar: tabs `v1` `v2` … (the label is just `v<n>`; the selected tab is inverted — background `--fg`, text `--panel`, weight 600 — so it reads the same in light and dark, the others are outlined chips), a summary line `v1 → v2: 1 section added · 1 changed · 1 removed · Instruction: <text>` (counts of `diffs[n]`; `Rejection:` / `却下理由:` for a rejection; `v1: first version` for the first) with bold labels, and, while an earlier version is shown, a note `Showing v1 (the decision is on v2)`. The current version is selected on show; `<` / `>` (and a click) move between versions (`logicalKey` maps Shift+`,` / `.` for an IME; the keys were free). The selected version goes through the usual plan renderer with markers from its own diff: a new section gets a `New` / `新規` badge, a changed one `Changed` / `変更` (badges only, no left bar); in a changed section the new line has a yellow tint and the line it replaced is shown struck through above it (a `del` followed by an `add` are paired; a lone `del` is a struck line, a lone `add` a tinted one; matching is by the line's text, so lines inside code blocks and tables are not marked). New and changed sections start open (once per set of versions); removed sections are only counted in the summary and are visible in the earlier tab. An earlier version is a flat read-only document (no folding, no read marks); the instruct box and the options stay for the current decision, and the section read state belongs to the current version only. The first version has no markers. The hint line gains `< > Version` (a `.vh` span that is shown once versions exist). Strings: the `ver_*` keys of `i18n.js`. **Reject without a reason:** the reason box is optional (placeholder `Reason (optional; Enter sends, Esc cancels)` / `却下の理由（任意。Enter で送信、Esc で取りやめ）`); "Send rejection" is always enabled and Enter in the empty box sends `{ approve: false }`; `n` still just opens the box.
- **Plans flow in like questions (PL3b).** The files in `~/.claude/plans` are items next to the pending decisions; there is no `p` browser. The GUI keeps `plans` (`GET /api/plans` on load and on every SSE reconnect, then `plan.updated` / `plan.removed`) and the bodies it needs (`GET /api/plans/:name`). A plan is **new** when it is unread and its `mtime` is under 24 h old; only new plans **whose session is known** (`session_id`) are auto-shown and counted (the server announces a session found later with `plan.updated`, and the plan then counts as new). The "Pending N" count and the drawer are decisions plus new plans (a plan row: title, `plan` / `計画`, age, `N sections · M lines`, a `●` mark; `▸` when shown). Screen choice when nothing is being looked at: pending decisions, then the newest new plan, then idle; a decision that arrives while a plan is shown takes the screen (the plan keeps its state and is next). `shownId` is a decision id or `plan:<file name>`.
  - **Plan screen (read only).** Header row 1 is the plan title, row 2 is `plans/ · Plan` / `計画` + `updated 5m ago` / `更新 5分前` (ticking) + the PL1 stats + the file name. The left column is the PL1 folding view (short plans whole); the right column holds the Instruct card (when the session is known) and one text action `Done reading` / `読んだ` with `Esc`; a long plan has the two zones too (the plan zone first; `→` lands on the Instruct card and focuses its box, `←` in the empty box goes back; with no session there is no options zone). No Approve / Reject, None of these / Can't answer; `y` `a` `n` do nothing. **Done reading** (`Esc` or a click) POSTs `/api/plans/:name/read {mtime}` (not for a plan that is already read), then goes to the next decision, else the next new plan, else idle. Reading is never marked silently (opening every section does not mark it).
  - **Live update.** On `plan.updated` for the shown plan the body is fetched again and the sections' open / read state is carried over by `sections[].hash` (same heading, level and hash = unchanged): changed and new sections are closed, unread (`☐`) and show an `updated` / `更新` word until opened; removed sections go; the scroll position is kept. When only the `mtime` moved (same text) nothing is redrawn. `plan.removed` for the shown plan goes to the next item or idle without a message.
  - **Upgrade in place.** The PL1 state (open, read, selected section, zone, `updated`) is keyed by the plan file name (`plan:<name>`) when a decision has `request.planFilePath`, else by the decision id. When an `approve_plan` decision for the shown file arrives it takes the screen with the same state (the plan row leaves the drawer, row 2 becomes "Approve this plan?", the buttons appear); a state that no longer fits the text is carried over by heading. Answering it POSTs the plan read (the plan is kept out of "new" while the answer is in flight, so the SSE echo cannot bring it back).
  - **Idle screen.** Plain `Nothing to decide`; no plan is listed. A plan that has been read, or that is unread but older than 24 h, is not shown anywhere (it stays on disk and in the API).
  - **Keys.** `[` `]` and `Tab` cycle through all items; `h` `l` `←` `→` cycle too, except on a long plan, where they are the zone keys (see above). `p` and the `p Plans` footer are gone.
- **Select = send (V1).** On a single select with one question, clicking a card POSTs it at once; `↑` / `↓` still move and `Enter` sends the card under the cursor (once); `1`-`4` send that card directly without moving the cursor (ignored while a text field has focus, and for multi select). The free-text field sends on Enter (empty: nothing; it is a one-line field, so no Shift+Enter). A reason row of None of these / Can't answer sends when clicked (Undefined terms sends the ticked words; untick first with Space or a click on the word; with nothing ticked the click sends nothing and the red line says why). The blocker's three cards behave the same. Plan keeps its three buttons (one click; `y` / `a` keep the double press when irreversible). Multi select (`Space` toggles, `Enter` sends) and several questions keep the Answer button.
- **Answers are sent at once.** Enter POSTs the answer immediately (there is no cancel window and no "Sent in N…"). The one thing kept is a confirmation, not a wait: when the decision is `irreversible`, or the chosen option's risk cell says it cannot be undone (`UNDO_BAD_WORDS`), the first click / Enter / digit selects that card and shows a red line inside it ("Press the same key or click again (3s)" / ja 「同じキーかクリックをもう一度(3 秒)」; released after 3 seconds, or when another card is clicked or the cursor moves) and the second send of the same card within 3 seconds goes out. The blocker's "Stop here" counts as irreversible. Plan approval is not part of this: one press always sends.
- **Long text folds** (it does not trigger when the hook's length limits, spec 3.6, are respected). Headline 2 lines, each card body line 2 lines (`-webkit-line-clamp`; the card under the cursor is whole), the plan's scope section 8 lines. `.` or a click on the headline or the "Show all" button toggles everything (state is per decision).
- After answering, the GUI moves to the oldest pending decision, or to the empty state.
- **Toasts**: stacked above the submit button (`.actions`), at most 3 (bottom right only when nothing is shown). Answer / copy / "Delivered" (your own answer settled, or a background decision answered) last 2 seconds. When a decision that is not shown is lost (`answer_lost` / `hook_disconnected` / `fallback`, or `cancelled` after answering), a red 4-second toast says "<title> did not reach the agent (reason)". A decision that was never answered and became `cancelled` gives a red 4-second "<title> was cancelled".
- **Wide diagrams**: when a diagram's natural width exceeds 1.5x the column width, a "Full width" text button appears above it. `f` (or the button) hides the decision column and shows the diagram at full width (horizontal scroll if needed). While full width, `Enter` is disabled (no submit); `Esc` / `f` / `Tab` return. Switching decisions resets it.
- **Connection**: when SSE drops (including the first failure) a red banner "Cannot connect (<origin>). Reconnecting…" appears and the empty state says "Cannot connect". On recovery the banner clears and a green "Reconnected" toast shows for 2 seconds. On 401 the GUI refetches `GET /` to renew the cookie and retries once (still 401: "Reload the page"). SSE reconnects after 2 → 4 → 5 seconds (cap) and refetches the pending list on reconnect (vanished decisions are dropped).
- **Images**: only `data:` `<img>` survive in explanations (external, relative and same-origin `src` are removed). Inline `code` wraps at the column width (`overflow-wrap: anywhere`); words containing `-` (such as `--port`) are wrapped in a nowrap span with `<wbr>` between words so they are not split (`textContent` is unchanged; code inside `pre` is untouched). The `copy` event strips U+2060 from copied selections.
- **Connection banner layout**: `#banner` is row 1 of the `body` grid (normal flow), the header row 2. While shown it pushes the header and the two columns down, and no vertical scroll appears.
- **Few boxes (≤ 2 means: the header's reversibility mark + the right column's cards).** In the left column `path:line` / commands under What I checked are plain monospace (`.cbadge`, still click-to-copy), not boxes.
- **Footer row (`#foot`)**: the key hint is one line at full width (short form below 900px); the `build <v>` stamp is fixed at the bottom right. While None of these / Can't answer is open the cursor card is not highlighted. On every SSE `open` the GUI reads `/api/config`; a different `build` reloads the page (typed free text is kept in `sessionStorage`). Card labels lose a trailing `(Recommended)` / `(推奨)` (the value sent is unchanged); a blocker's three fixed labels are shown in the display language.
- **No faint text (TX1, pattern "frames and rules").** Text is never a lighter colour or translucent: every piece is `--fg` (light `#1d1d1f`, dark `#e8e8ec`), plus the accent / status colours (accent blue, repo colour, red, green; the blocker band's dark text on orange). Hierarchy is structure, weight and position, at the sizes the screen always had (secondary 12 px): the header's context row is **outlined chips** (`.chip`: 1 px `--line` border, 2 px radius, `1px 6px` padding; the repo chip has the repo-colour border and a 600 name; then `⎇ branch`, `⧉ worktree`, scope, age; a plan approval adds a chip for `9 sections · 200 lines · 12 files` and the file name as text; on a blocker's band the chips get a dark border), the **Goal row** has a 600 label (`Goal` / `目的`, no colon, from the existing `goal` key) and a 1 px rule under it, the **condition** line starts with a 600 label (`Condition` / `条件`, key `cond_label`), option titles are 600 over 400 descriptions, and the footer hint's key names are bold (`boldKeys` in `app.js` bolds the first word of each ` · ` item when it is a key). `--muted` (light `#55555b`, dark `#b0b0b8`, both ≥ 6:1 on the panel) remains only for `::placeholder` and disabled controls, which are also told apart by a dashed border and a tinted background. `test/gui/contrast.test.ts` sweeps every visible text on a question, checkpoint, plan, blocker and the settings page in both schemes (computed colour is `--fg` or an accent, ≥ 7:1, no `opacity`; the blocker band's dark-on-orange text is 6:1) and checks the chips, the goal rule, the condition label and the bold key names.
- **Few boxes.** A box (chip / badge / pill) is used for the reversibility mark when it is not "reversible" and nothing else; the card's "★ Recommended" is text. Option colours are the card's left border, a coloured label, a dot in the compare table and the Mermaid nodes. The drawer rows carry at most one small mark (`●` waiting for you, `(no explanation)`, `▸` shown). "Show all", "Full width" and the pending count `☰ N` are underlined text buttons.
- **No key badges.** There is no `<kbd>` element anywhere. The only key guidance is **one plain hint line (12 px; the key names are bold) at the bottom of the right column** (`↑↓ Move · Enter / click / 1-4 Send · ? Terms · e Evidence · v Compare · y Copy · n None of these · x Can't answer · s History · ←→ Next · Esc`; the short form below 1100px wide or 820px tall; the drawer has its own one-line plain text). "Show all", "Full width" and "Pending N" are small text buttons. Everything can be answered with the arrow keys alone. Question: `↑` / `↓` move (single select: move = select, stops at the ends), `Home` / `End` jump to first / last, `Space` toggles in multi select, `Enter` sends the cursor card, `1`-`4` send card 1-4. **A card that carries a text box (the free-text card, the checkpoint's instruction card) takes the focus the moment the cursor lands on it** (↑ ↓, `Home` / `End`, a click anywhere on the card; caret at the end of the existing text; the first render does not steal the focus; the hint line says `Type your reply · Enter send · Esc back`). In the box: digits and letters (including `j` / `k`) are text — only the arrows leave an empty box — `Enter` sends (empty: nothing), `Esc` blurs it and returns to card navigation without losing the text, `↑` / `↓` with an empty box blur it and move to the neighbouring card (with text they are text-field keys). Moving the cursor off the card blurs the box. The Can't answer / None of these note boxes are not cards and still take the focus with `i`. Plan: `↑` / `↓` move between the instruction card, Approve and Reject (the cursor starts on Approve; with a contents the arrows move the contents and `i` / a click reach the card) and `Enter` on a button decides (on the card it focuses the box) (`y` / `a` / `n` work too; `n` opens the reason field, `Esc` cancels). Common: `←` / `→` / `h` / `l` (`Tab` / `Shift+Tab`) previous / next pending, `b` opens the drawer, `.` expands or folds, `c` copies the first code block (blocker), `f` toggles full width for a wide diagram. In the drawer: `↑` / `↓` (`j` / `k`) move, `Enter` switches, `Esc` / `b` / `←` close. Letter keys: `j` `k` `gg` `G` `i` for questions, `j` `k` `y` `a` `n` for plans. Movement keys work even when a button has focus. There is no fallback button (the API's `{fallback:true}` remains but the GUI never sends it).
- Each question card shows "Free text" under the options (a radio for single select, a checkbox for multi select) with a text input. When chosen, the answer value is that string (in multi select it is appended after the chosen labels). An empty string cannot be sent.
- `GET /` appends a version to the `app.js` / `app.css` URLs (`?v=<mtimeMs in base 36>`; `/public/*` ignores the query), and `app.js` shows a small `build <v>` at the end of the hint line (bottom right in the empty state), so you can tell whether you are looking at a stale build.

## Progress checkpoints (`kind: "checkpoint"`)

A recap Claude Code wrote into the transcript becomes a non-blocking card (the server makes it; nothing waits on the answer).

- **Header.** Row 1 is the title `Progress check · <session title or cwd basename>` (`進捗確認 · …`), row 2 the context line. The top of the left column is the Goal row, then a line `The agent keeps working if you do not answer`, then the recap (whose first sentence is the headline, so none is drawn separately). The Goal row works as for any decision.
- **Left column**: the recap in full (`.cp-recap`, plain text, line breaks kept).
- **Right column** (`renderCheckpointRight`): three cards, keys `1`-`3`, `↑↓ j k` move, Enter acts on the cursor card. `Continue` (recommended, `1`) sends `{kind:"continue"}` and `Stop here` (`3`) sends `{kind:"stop"}`, both on one press (no second press). `Give an instruction…` (`2`, `i`, a click, or the cursor landing on it with ↑ ↓) focuses its text box at once; Enter in the box sends `{kind:"instruct", text}` (an empty box sends nothing). There is no None of these / Can't answer and no free-text row. A note `The agent is idle; your reply arrives at its next tool call` (`.cp-idle`) is shown while the session state (`GET /api/sessions`, SSE `session.updated`) is `idle`.
- **Order and count.** Blockers, then questions and plans, then checkpoints (each oldest first), then the new plan files. A question or plan approval that arrives while a checkpoint is shown takes the screen (unless an instruction is half typed). Checkpoints count in `Pending N`; the drawer row shows the word `recap` / `進捗` in place of `Question`.
- **After.** An answered checkpoint leaves like any decision. A `cancelled` update (superseded, new prompt, session end, expired) removes it with no toast.

## Rich decision screen (explanation file extras)

All extra sections are optional and are matched exactly (English first, Japanese alias): Terms / 用語, What only you know / あなたにしか分からないこと, Assumptions / 前提, Counterargument / 反論, Affected / 影響を受けるもの. They are read only for a single question whose Options table maps onto the options (the cards); otherwise they stay in the left column as plain text. Terms, unknowns, assumptions, counterargument and affected leave the body and go to the lead of the left column.

- **Three layers.** 1 second (the header): the title (with the reversibility mark when costly), the context line (repository / branch / worktree, scope, age) and, as the first paragraph of the left column, the **headline** (the first sentence of the Recommendation, *moved* out of the box like the TUI: the lead's box shows the rest, and there is no box when the recommendation is one sentence and has no callout). 10 seconds (the right column): the option cards (bodies fold at 2 lines, the cursor card is whole; extra table columns are headed rows), None of these and free text. 60 seconds (the left column): the lead (Why, Recommendation body, "You decide:", "Against this:", Assumptions; Affected is folded at the end), then What I checked with footnotes, the diagram, the diff, then any unknown H2 section as written, and the `?` / `e` / `v` views.
- **Cards stay in view.** With one question, `#decision` does not scroll: `.q-top` (only the blocker's "what you need to do" box; at most 52vh, 58vh when the window is 820px tall or less) and `.q-cards` (the option cards, None of these, free text) which is the only scrolling region. Cursor moves, `.` and the first render scroll `.q-cards` so that the cursor card is fully visible (`revealCard`); the Answer button is sticky below. Tested at 1440x900, 1280x800 and 1000x700: the header, the cursor card and the Answer button are inside the viewport. Below 1100px wide or 820px tall the hint line is the short one (`hint_short_*`), so it stays on one line. Below 900px everything scrolls as one page again.
- **Unknown sections.** An H2 section whose heading the GUI does not know is never dropped: it is shown as written at the end of the left column (known sections that move to the lead leave the body).
- **Weight.** See "Answers are sent at once": the confirmation (Enter twice) is the only brake.
- **None of these (`n`, question cards only).** Opens four types (Missing option / Wrong premise / Need more evidence / Ask me later; ↑↓ and Enter, `i` for a one-line note). The answer is the free text `None of these — <type>: <note>` (`None of these — <type>` without a note; the type is always the English name). It never needs Enter twice (it chooses nothing irreversible) and is sent at once. On a plan `n` still rejects.
- **Terms.** The first occurrence of each term in the text (Why, cells, recommendation, assumptions, counterargument, unknowns, headline) is a dotted-underlined `.term[data-def]`; hover or focus shows the definition; `?` lists them all. Option labels in the text get the option's color first (a `<strong>` / `<code>` equal to a label, or plain text for labels of 3+ characters).
- **Option colors.** Option index → `--opt-0..3` (the recommended one is the accent): the card's left border and coloured label, mentions in the text, and Mermaid nodes whose label is an option label (shape `stroke`, label `fill` / `color`).
- **Footnotes.** `[^n]` in the body becomes a superscript with the evidence as its tooltip; the definitions are appended under What I checked. `e` scrolls to (and flashes for 1 second) the footnote last hovered or focused, else the next one. `path:line` and `` `cmd` `` under What I checked are monospace badges; `y` (or a click) copies the hovered / focused one, else the first. Numbers with a unit are lightly emphasized.
- **Compare (`v`).** With extra columns, an overlay table (rows = columns, columns = options, the recommended one tinted); ↑↓←→ pick an option, Enter answers it (through the same confirmation), `v` / `Esc` close.
- **Code.** `diff` fences color file headings, `+`, `-` and `@@`. Fences with a language get highlight.js. In the risk column `UNDO_BAD_WORDS` ("cannot be undone / restored / reverted", irreversible, permanent, 戻せない…) are red first, then the remaining `UNDO_WORDS` (undo, revert, restore, 戻す…) green and underlined, at word boundaries for English ("cannot be restored" is red only).
- **New keys** (question cards): `?` terms, `e` evidence, `v` compare, `n` none of these, `y` copy badge. They do not collide with `↑ ↓ Enter ← → Space Esc b c f . h l i`. They are listed only in the bottom hint line.

## Can't answer this (`x`, question cards only)

The second way out next to None of these: the options are fine but **the explanation cannot be read** (typically internal codes such as `W-T2` / `FT4` nobody defined). Both sit in one quiet row under the cards as underlined text buttons; the panels have a left rule only and no box. There is nothing on a plan screen (reject is enough). Neither is a cursor stop (None of these is not either).

- **Panel.** Three reasons (↑↓ / `j` `k`, Enter or a click on the row sends at once: no Enter twice, no wait): `Undefined terms`, `Unclear`, `Too much at once` (en "Undefined terms / Explanation unclear / Too much at once", ja 「分からない用語がある / 説明が分からない / 一度に聞きすぎ」). The suspicious identifiers are listed under `Undefined terms`, all ticked; the cursor walks the reasons and the terms in one list, `Space` ticks / unticks a term, `i` focuses the one-line field (under Undefined terms: Enter adds a term; under the others: a note; Enter on an empty field sends). With nothing ticked Undefined terms cannot be sent (one red line says so; there is no send button). `Esc` / `x` close, `n` switches to None of these. The default reason is `Undefined terms` when any suspicious identifier was found, else `Unclear`.
- **Value** (always English): `Cannot answer — Undefined terms: W-T2, FT4` / `Cannot answer — Unclear: <note>` (`Cannot answer — Unclear` without a note) / `Cannot answer — Too much at once[: <note>]`.
- **Suspicious identifiers.** `coinedTerms(v2)`: the `// <coined>` block of `app.js` is a copy of `COINED_ALLOW` / `COINED_TOKEN` / `COINED_PHASE_*` / `extractCoined` / `termDefines` in `src/hook/explain.ts` (`test/gui/cannot-rules.test.ts` runs the copy and compares it with the original). Scanned: the front matter `title` and the body outside code fences (inline code counts, Terms included). Exempt: `question`, `recommended`, option labels, and terms defined under Terms with at least 12 characters (a pointer such as "the plan item" does not count). In the text each occurrence is a dotted red underline (`.term-undef`, tooltip "Not defined under Terms"); a click opens the panel with that word ticked (added when the scan did not find it). The header title is not marked. A Terms entry that defines nothing stays red instead of getting the `.term` annotation.
- **Keys / hint.** `x` joins the bottom hint line (`x Can't answer`; the short line gets `x` in its letters); it fits on one line at 1000x700.

## Session history (`s`)

What the session is about, without boxes: the Goal row and one panel. Data: `GET /api/decisions/:id/history` (spec/api.md; first instruction, total, the last 20).

- **Goal row (the first element of the left column, above the headline).** `Goal <first instruction>` at 12 px, the label `Goal` (ja `目的`) 600, the rest 400 and a 1 px rule under the row: whitespace and newlines folded, one line, ending in `…` (CSS ellipsis on `.goal-text`), then `· N instructions` (ja `· N 件`) when the session has 2 or more. No history (unreadable or missing transcript, request failed) = no row; nothing is reserved. No Session box and no History chip. A click on the row opens the panel (the handler is on the row itself).
- **Fetch.** Lazy, when a decision is shown (`loadHistory`, from `renderHead`). Cached per `session_id` for 5 minutes, concurrent shows share one request, so a second decision of the same session does not fetch again. A failure is ignored and not cached, so the next time the decision is shown it retries. Switching the display language re-renders from the cache.
- **Panel (`s` or a click on the Goal row).** The same overlay machinery as the `?` Terms list (`openOverlay`); opening one closes the other (`s` in the Terms list swaps to history, `?` in the history swaps back). Rows are chronological: relative time (`3h ago` / `3時間前`), a `first` mark (`最初`) on the first instruction, one line of text. `↑` / `↓` (`j` / `k`, `Home` / `End`) move; `Enter` or `.` (or a click) shows the full text (`white-space: pre-wrap`, line breaks kept); `Esc` goes back to the list, `Esc` again (or `s`) closes. Digits, `x` and `n` do nothing inside. `recent` overlaps `first` for a short session: it is not shown twice (same rule as `historyItems` in `src/tui/history.ts`). Text is shown as written, never rendered as Markdown.
- **`s` is a letter** in a text field. It is off while the "Can't answer" or "None of these" panel is open, and when there is no history. The hint line gets `s History` (ja `s 履歴`) only when the session has more than one instruction, as the TUI footer does.

## No options and Approval (Codex)

- **No options** (a prose question picked up by the Stop hook): free text only. The None of these / Can't answer row is not drawn, `n` / `x` do nothing, and the footer hint no longer lists them. The same holds for a Codex approval (`header: Approval`): Allow / Deny only; its backticked command is monospace in the question and in the header title, and the blank line between the description and the command is kept.
- **Display-language headings (Y3).** "Why this decision is needed now" / "Why I stopped" are captioned from `sec_why` / `sec_blocker_why` like the other known sections. On the blocker band the title is dark (`#1d1d1f`) for contrast. The free-text card is one row (label and input side by side) and below 1100px wide card bodies fold at 1 line, so 3 cards + free text + hint fit at 1000x700.
- **Approval** (the question's `header` is `Approval`; options Allow / Deny): the question is shown at the top of the right column with each backticked command in monospace (`.approval-cmd`). The Deny card is never weighty: a risk cell saying "cannot be undone" does not make it need a second click.

## Accessibility and motion (UX1)

- Announcements: two fixed, visually hidden live regions in `index.html` (`#live` polite, `#live-urgent` assertive). `toast()` writes to them (lost / cancelled toasts are assertive); the visible `.toasts` box is `aria-hidden` because it is re-parented on every render. A new pending item announces `New decision, {n} pending` (including the first one on an empty queue; the initial load is not announced).
- Drawer and overlays: the closed drawer is `inert`; while the drawer or an overlay (`?` / `v` / `s`, `role=dialog aria-modal`) is open, `#head`, `#main`, `#foot`, `#empty` and the pending button are `inert`. An overlay takes focus and gives it back to the previous element (never to a text box) on close.
- CSS: a global `:focus-visible` ring, `accent-color`, `overscroll-behavior: contain` on the scroll panes, `text-wrap: balance` (headings) / `pretty` (prose), 32 px targets under `pointer: coarse`, and `prefers-reduced-motion: reduce` turns transitions and animations off.

## ukagai Markdown

Explanations and plans are written in the dialect of `docs/spec/markdown.md`; the GUI renders it in `setMarkdown` (`app.js`, sanitizer first, then the dialect on the parsed DOM). Every construct has a plain-text fallback in the TUI.

- **Callouts.** `> [!NOTE|TIP|IMPORTANT|WARNING|CAUTION] Optional title`: coloured left border, the title (or the localised kind word) as the label. IMPORTANT is purple.
- **Task lists.** `- [x]` / `- [ ]` become ☑ / ☐ glyphs (read-only); done items are dimmed.
- **Folding.** `<details>` / `<summary>` (closed unless `open`), plus `<br>`, `<sub>`, `<sup>`. The sanitizer is an allowlist: every other tag is dropped (its text stays; `script`, `style`, `iframe`, `object`, `form` and similar go with their content), as are event attributes and `javascript:` links. A `<details>` inside a plan section folds on its own and does not touch the outline folding (`details.plan-sec` / `plan-sub` are the outline's).
- **Mermaid.** Any type of the vendored build (flowchart, sequenceDiagram, stateDiagram-v2, classDiagram, erDiagram, gantt, pie, mindmap, timeline, gitGraph, journey, quadrantChart, xychart-beta, block-beta). A render error shows the error line and keeps the source.
- **Code.** ```` ```ts title="src/x.ts" ```` puts a filename tab (text) above the block; `diff` colours `+` / `-` lines. Blocks over 9 lines still fold.
- **Badges.** `[done] [todo] [doing] [blocked] [risk] [skip]` at the start of a list item or table cell (or right after a bold title: `**Title** [done]`) become `.badge` chips; the word stays. Tokens elsewhere in a sentence are text.
- **Highlight.** `==text==` becomes `<mark>` (not inside code).
- **Columns.** `::: columns` … `---` … `:::` (2–3 columns): side by side from 900 px, stacked below.
- **Steps.** An ordered list under `## Steps` / `## 手順` becomes a timeline (numbered dots, a connecting line, the badge beside the bold title, nested content indented).
- **File references.** Inline code that looks like a repository path (`src/x.ts:12`, `public/app.js#L40-L60`) is a chip; a click copies it. In "What I checked" paths stay unboxed.
- **Images.** `![alt](path)` with a local path (relative to the document's directory, or absolute) is served by `GET /api/files?decision=<id>|plan=<name>&path=<as written>` (allowlisted folders, png / jpg / jpeg / gif / webp, ≤ 10 MB; see `docs/spec/api.md`). The image is capped at 100% width / 480 px height with the alt text as caption; a click opens a lightbox (the shared overlay: `Esc` or a click closes, focus returns to the image, the background is inert). A file that cannot be loaded shows the alt text and an "image not found". `http(s)` and other schemes are dropped. An `.html` / `.htm` target (`![alt](compare.html)`) becomes a `.doc-frame`: a caption row (alt, file chip, `Full screen` / `全画面` button) and `<iframe sandbox>` (empty attribute) 480 px high pointing at the same `/api/files` URL; the button opens it in the overlay (`.overlay.frame`, Esc closes).
